# 🧪 测试管理规则

## 📋 目标
建立统一的测试文件管理体系，确保测试代码与生产代码分离，提高测试可维护性和可执行性。

## 📁 目录结构

```
__test__/
├── unit/                    # 单元测试
│   ├── test_constants.py   # 常量测试
│   ├── test_crypto.py      # 加密模块测试
│   ├── test_archive.py     # 归档模块测试
│   └── test_utils.py       # 工具函数测试
├── integration/            # 集成测试
│   ├── test_encryption.py  # 加密解密集成测试
│   ├── test_cli.py         # 命令行界面测试
│   └── test_interactive.py # 交互模式测试
├── performance/            # 性能测试
│   ├── test_large_files.py # 大文件处理测试
│   ├── test_speed.py       # 速度性能测试
│   └── test_memory.py      # 内存使用测试
├── fixtures/               # 测试数据
│   ├── sample_files/       # 样例文件
│   └── sample_dirs/        # 样例目录
└── conftest.py            # pytest 配置文件
```

## 🎯 测试分类

### 1. 单元测试 (Unit Tests)
- **目标**: 测试单个函数或类的功能
- **范围**: 独立的模块、函数、类
- **执行频率**: 每次代码修改
- **要求**: 快速执行 (< 1秒)

### 2. 集成测试 (Integration Tests)
- **目标**: 测试模块间的协作
- **范围**: 多个模块组合的功能
- **执行频率**: 每次提交前
- **要求**: 覆盖主要使用场景

### 3. 性能测试 (Performance Tests)
- **目标**: 测试系统性能指标
- **范围**: 大文件处理、并发处理
- **执行频率**: 版本发布前
- **要求**: 性能基准测试

## 📝 测试文件命名规范

### 文件名格式
- 单元测试: `test_<module_name>.py`
- 集成测试: `test_<feature_name>.py`
- 性能测试: `test_<performance_aspect>.py`

### 函数命名
- 测试函数: `test_<functionality_description>()`
- 辅助函数: `_<helper_function_name>()`
- 固件函数: `fixture_<fixture_name>()`

## 🔧 测试数据管理

### 测试文件位置
- 所有测试文件必须放在 `__test__/` 目录下
- 测试数据放在 `__test__/fixtures/` 目录下
- 临时文件使用 `tempfile` 模块创建

### 清理规则
- 每个测试必须清理自己创建的文件
- 使用 `try/finally` 或 `with` 语句确保清理
- 测试套件级别的清理在 `conftest.py` 中定义

## ⚙️ 测试执行规则

### 测试运行器
- 使用 `pytest` 作为主要测试框架
- 支持 `unittest` 作为兼容选项
- 提供统一的测试运行脚本

### 执行命令
```bash
# 运行所有测试
python run_tests.py

# 运行单元测试
python run_tests.py --unit

# 运行集成测试
python run_tests.py --integration

# 运行性能测试
python run_tests.py --performance

# 运行特定测试文件
python run_tests.py --file test_crypto.py
```

### 测试覆盖率
- 目标覆盖率: ≥ 90%
- 核心模块覆盖率: ≥ 95%
- 使用 `coverage` 工具监控

## 🚫 禁止行为

1. **❌ 不在根目录创建测试文件**
   - 所有测试文件必须在 `__test__/` 目录下

2. **❌ 不清理测试数据**
   - 测试完成后必须清理临时文件

3. **❌ 使用硬编码路径**
   - 使用 `tempfile` 或相对路径

4. **❌ 测试间相互依赖**
   - 每个测试必须是独立的

5. **❌ 在生产代码中导入测试模块**
   - 测试代码与生产代码完全分离

## ✅ 最佳实践

### 测试编写
- 使用描述性的测试函数名
- 每个测试只验证一个功能点
- 使用断言而不是打印语句
- 提供清晰的失败信息

### 测试数据
- 使用小而精确的测试数据
- 避免使用真实用户数据
- 包含边界条件和异常情况

### 错误处理
- 测试异常情况的处理
- 验证错误消息的准确性
- 确保资源正确释放

### 性能考虑
- 单元测试必须快速执行
- 避免在测试中执行耗时操作
- 使用模拟对象替代真实依赖

## 📊 测试报告

### 报告内容
- 测试通过率
- 代码覆盖率
- 性能指标
- 失败原因分析

### 报告格式
- 控制台输出：简洁明了
- HTML报告：详细分析（可选）
- JSON导出：CI/CD集成

## 🔍 测试审查

### 代码审查要求
- 新功能必须有对应的测试
- 修复的bug必须有回归测试
- 测试代码也需要代码审查

### 持续集成
- 每次提交自动运行测试
- 测试失败阻止合并
- 性能下降发出警告

## 🔒 强制测试覆盖与验证规则

### ⚠️ 强制性要求（必须遵守）

#### 1. 代码更改测试覆盖要求
- **所有新功能**必须在 `__test__/` 目录中有对应的测试文件
- **所有修改的函数**必须更新相应的测试用例
- **所有修复的bug**必须添加回归测试，防止再次出现问题
- **所有新增模块**必须创建完整的单元测试套件

#### 2. 测试验证流程（强制执行）
```bash
# 开发流程中的强制测试步骤
1. 编写生产代码 → 2. 编写/更新测试 → 3. 运行测试 → 4. 验证覆盖 → 5. 提交代码
```

#### 3. 测试覆盖率检查
- **最低覆盖率要求**: 90%
- **核心模块要求**: 95%（crypto.py, main.py）
- **新增代码要求**: 100%（必须全部覆盖）
- **分支覆盖要求**: 85%（条件语句和循环）

#### 4. 强制验证命令
```bash
# 每次代码更改后必须执行
python __test__/run_tests.py --unit           # 必须通过
python __test__/run_tests.py --integration    # 必须通过
python __test__/run_tests.py --performance    # 性能不下降

# 覆盖率验证（如安装coverage）
coverage run -m pytest __test__/
coverage report --show-missing
coverage html  # 生成详细HTML报告
```

### 🚫 违反强制规则的后果

#### 自动阻止机制
1. **CI/CD 自动失败**：测试覆盖率不达标时自动阻止合并
2. **代码审查拒绝**：同行评审时必须检查测试完整性
3. **版本发布阻止**：未通过全部测试的版本不能发布

#### 具体违反情况
- ❌ **新增功能无测试**：直接拒绝合并请求
- ❌ **修改函数未更新测试**：要求补充测试后才能合并
- ❌ **覆盖率低于90%**：必须提高覆盖率或通过审查
- ❌ **核心模块覆盖率低于95%**：强制要求达到标准

#### 监控指标

- **平均测试执行时间**：监控性能趋势
- **测试失败频率**：分析稳定性
- **覆盖率变化趋势**：确保不下降

#### 质量门槛
```python
# 强制质量门槛配置
MIN_COVERAGE = 90  # 最低覆盖率

MAX_TEST_TIME = 60  # 最大测试执行时间（秒）

```

### 🔍 测试审查要求

#### 代码审查检查点
1. **测试完整性**：每个功能都有对应测试
2. **测试质量**：测试用例设计合理
3. **覆盖范围**：边界条件和异常情况被覆盖
4. **测试独立性**：测试间无相互依赖
5. **清理机制**：资源正确释放和清理

#### 审查问题分类
- 🔴 **阻止性问题**：必须修复才能合并
- 🟡 **警告问题**：建议修复但可酌情通过
- 🟢 **建议改进**：非强制性的最佳实践建议
